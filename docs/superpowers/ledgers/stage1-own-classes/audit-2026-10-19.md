## Broken

### B1. The waiver link in every class confirmation email goes to a dead page
- **Where:** `src/lib/classes/confirmation.ts:41` builds `/waiver?workshop=cls_…`. `src/lib/events.ts:126-139` `getEvent('workshop', id)` only asks Square (`findWorkshop`), so a `cls_` id gives null. Callers: `src/pages/waiver.astro:40`, `src/pages/api/waiver/sign.json.ts:309`.
- **Why it matters:** every family who books one of our classes gets an email whose "sign the agreement" link can't find the class, so nobody can sign ahead. Print day's waiver column (`day.json.ts:74`) will always say "No waivers signed yet". The door check-in can't open the class either (see N1).
- Noted for Task 14 in the ledger; listed here because the email already goes out today.

### B2. A refund made in Square isn't counted on our side, so a person can be refunded twice (R26 missing)
- **Where:** `src/lib/classes/square-events.ts:331` (no returns) and `:357` only write a `refund-flags` entry. The money is never put on the ledger. `src/lib/classes/refunds.ts:86` `bookingCap` and `remainingOn` (line 67) only see refunds made through our own flow.
- **Why it matters:** say Catherine refunds $25 for one person on the Square POS, on a $50 two-person booking. /admin still shows $50 refundable. Kaden presses "Refund one person" on the same person and Square accepts it, because $50 is still within the payment. One person is refunded twice. Square only refuses once the payment total is exceeded.
- **Status:** the Task 13 review finding is still open.

### B3. The nightly catch-up will probably time out before it reaches the newest sales (per-order catalog call)
- **Where:** `square-events.ts:220-227`. `handleOrder` calls `classLike()`, which is one Square `catalog/batch-retrieve` per order, whenever an order has any line that isn't ours. That is every Craft Café and party order. `reconcileClasses` (`:411-448`) runs them one after another, oldest first (`sort_order: 'ASC'`), inside an ordinary site route (`src/pages/api/jobs/reconcile-classes.json.ts`). Netlify cuts that route off after about 10 s by default (26 s at most).
- **Why it matters:** a busy weekend has around 100 orders in 48 hours, and each one takes a 150–300 ms Square call, so the run dies part way. The orders it never reaches are the most recent ones, which are the sales a missed webhook most likely dropped. The safety net is weakest exactly when it's needed.
- **Status:** the Task 13 review finding is still open.

### B4. A refund the webhook misses is never caught (R25 missing)
- **Where:** `reconcileClasses` (`square-events.ts:411`) only searches orders. There is no `GET /v2/refunds` (ListPaymentRefunds) pass.
- **Why it matters:** if the refund webhook is dropped (for example while the signature key isn't set, see B5), a POS return never frees its seat. The class stays "full" and the seat can't be resold.
- **Status:** the Task 13 review finding is still open.

### B5. Square's messages to the site are refused until two settings exist on live, and the setup doc names the old domain
- **Where:** `src/pages/api/webhooks/square.json.ts:33-51`. With no `SQUARE_WEBHOOK_SIGNATURE_KEY` the site answers 500. With no `SQUARE_WEBHOOK_URL` every signature check fails (it hashes `'' + body`), so the site answers 403. `docs/square-setup-guide.md:63,84` still says `homegrowncraftstudio.com`, which 301-redirects, and Square won't follow a redirect on a POST.
- **Why it matters:** POS sales and Square refunds of our classes never reach the seat ledger. The only fallback is the nightly run, which has its own problems (B3, B4). This is a launch prerequisite on Kaden's list: subscribe to the webhooks, then set both settings to `https://ourhometownstudio.com/api/webhooks/square.json`.

### B6. If the two class settings are missing on live, our classes can't be sold, or taxable classes go out with no tax
- **Where:** `src/lib/classes/square-catalog.ts:105-108`. With no `SQUARE_CLASSES_CATEGORY_ID` every POS sync throws ("Classes category isn't set up yet."), and `book.json.ts:178-184` then refuses every booking ("isn't on the POS yet"). With the category set but no `SQUARE_CLASS_TAX_ID`, taxable classes are pushed with no `tax_ids`. Square then charges no tax, and `book.json.ts:223-236` charges Square's lower total without a word, because only an upward difference emails the owners.
- **Why it matters:** the first case is a dead booking button. The second is 9% tax silently not collected. Neither setting is in `.env.example`.

## Incomplete (built in part)

### I1. Crew refunds: the server side is built, but /staff has no screen for it
- `src/pages/api/staff/class-refund.json.ts` exists and requires a reason. Nothing in `src/components/staff` calls it. The spec decision "crew refund with a reason, logged with their name" can't be used yet.

### I2. Refunds and counter sales that need a person are recorded, but shown nowhere
- `listRefundFlags`, `listUnmatchedPos` and `listPosNeedsDays` (`square-events.ts:458-486`) have no caller. Neither /admin nor /staff warnings shows "Free a seat?", unmatched POS sales, or counter sales of a pick-your-days pass. `resolveRefundFlag` records the decision only. There is no setter to move a counter seat to the right days (R27, Task 14).
- **Why it matters:** a plain Square refund or an unknown POS sale sits silently in a store nobody reads.

### I3. Cancel doesn't show who is booked before you confirm, and there's no "Refund everyone"
- `src/components/admin/classes/ClassBookings.tsx:111-124` asks "Yes, cancel the class" and only lists people after cancelling. The spec says Cancel shows everyone booked and asks to confirm, with "Refund everyone" as its own separate confirm. Neither the list-before-confirm nor "Refund everyone" exists. (The server side is right: `cancelClass` never refunds.)

### I4. Library versions don't say which owner made them, or what changed
- `ADMIN_BY = { id: 'admin', name: 'Owner' }` (`admin-actions.ts:28`) is stamped on every save, because /admin is a single shared passcode. A version's note is free text or "Updated while scheduling …", not a list of changed fields. Restore (`LibraryList.tsx:118-120`), "Just this date / Also update the library" (`ClassEditor.tsx:568-569`) and recording the version a scheduled class came from (`scheduleClass`/`duplicateClass`) are all built.

### I5. Minimum to run is stored but never acted on, and only takes a date
- The editor (`ClassEditor.tsx:199-200`) saves the decide-by time as noon on the chosen date, so the spec's "by Thursday 5 PM" can't be set. No text or email alert is ever sent (Task 15).

### I6. The waitlist cutoff can't be set
- `waitlistCutoffHours` is in the type and validation (`validate.ts:22,62`) but has no field in `ClassEditor.tsx`. The waitlist itself is stage 4. `onSeatFreed` (`refunds.ts:194`) is a no-op hook, which is as planned.

### I7. Joining partway vs. sign-ups closing before the first session: mostly right, one open question
- `pricing.ts:44-56`: a "remaining" pass is refused once the class has started when `joinPartway` is off. "All" and "fixed" passes close at their first session. A "choose N days" pass still sells later days after the class has started even when `joinPartway` is off. Kaden should say whether "sign-ups close before the first session" should also stop single-day passes.

### I8. Print a day: built, but waiver status can't fill in for our classes
- `src/pages/api/admin/classes/day.json.ts` and `PrintDay.tsx` cover rosters, prep counts and waivers. For our classes the waiver column is always empty until B1 is fixed.

### I9. The /admin layout the owner rejected is still the one in place
- Owner feedback on 19 Oct: "the entire Admin UI/UX sucks", and a new class should land in the library without him thinking about it (R21). Direction D is approved and Task 11b is briefed (`task-11b-brief.md`), but not built. Today a class made with New class only reaches the library if "Also update the library" is pressed.

### I10. The Square-side pieces of Task 13 are each partly done
- `?force=1`, so an owner can run the catch-up on demand, is missing: the route only acts at 3 AM (`reconcile-classes.json.ts:42`).
- On a split-tender POS sale only the first tender's payment id is kept (`square-events.ts:185-186`), so a refund on the second tender is ignored as "not ours".
- A plain refund is flagged against only the first class when one payment covers several classes (`:331`).

## If this branch merged to production today

1. **Our classes would sell, but the studio couldn't run them.** /staff can't see them (N1), the waiver link is dead (B1), there are no reminders (N2), and POS sales or refunds made in Square don't reach the ledger unless the webhook settings are in place (B5). Owners should create no customer-facing class until N1 and B1 are done.
2. **The party date picker and party booking now refuse times when our own class store or blocked time can't be read** (`party-availability.ts:54-70`), where before they never blocked. This is intended (R10/R11), but it is a change in live party behaviour: a Netlify Blobs outage now hides party times.
3. **Legacy Square classes are unchanged on live.** The sandbox short-cut (`providers/square/workshop.ts:241-291`) only applies when `SQUARE_ENVIRONMENT=sandbox`.
4. **Blob stores:** live has no `STORE_NAMESPACE`, so it uses the live names, which is correct. `blobStoreName` throws for any Netlify deploy that is on the sandbox without a namespace. Check the `dev` branch-deploy context's `SQUARE_ENVIRONMENT` before merging, because a sandbox dev preview with no namespace would fail on every store. The same commit (e3a84d8) also changes party and kit checkout to follow the configured Square environment instead of always using production, so prod must keep `SQUARE_ENVIRONMENT=production`, which it does today.
5. **Payment bypass:** simulated payments (`book.json.ts:78,170-177`) need both `DEV_BYPASS_PAYMENT=true` and a preview/dev request (`dev-flags.ts:20-27`), so they can't be reached on live.
6. The "Set up sandbox" panel appears on live /admin (M1). It is harmless.
7. The settings in B5 and B6 must be set on live before the first class is made.
