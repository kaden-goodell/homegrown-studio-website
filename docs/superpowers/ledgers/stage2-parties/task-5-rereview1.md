## Targeted hunts
1. **`extendHold` rebuild racing a new hold for the same time: correct.** The rebuild check (:264) runs inside `mutate` against the fresh `live` list. If another server's `holdTime` lands first, our `setIfMatch` fails (Netlify `onlyIfMatch`, or `onlyIfNew` when the doc is missing). The retry re-reads, sees the rival, and returns `held: false` with a clash, so we never write on top of a rival. The reverse order works too: `holdTime` on the other server loses its CAS, re-reads, and gets `taken`. An expired copy of our own hold is left out of `live`, so it neither blocks the rebuild nor gets duplicated.
2. **"Only grows" with null expiry: correct.** `laterExpiry` returns null whenever either side is null. That holds in the `holdTime` replay (a 10-min hold replayed by a link hold becomes never-expiring, and a 10-min replay of a link hold stays never-expiring) and in `extendHold`. A booked time is never touched by `extendHold`. `confirmTime` always sets null. The no-op comparisons use the same string that `later`/`laterExpiry` return, so an unchanged hold is not rewritten.
3. **The 10-s timeout lets go of the lock while a write may still land. Can two writers both succeed? No.** Every write is a store-side conditional (`onlyIfMatch` on the etag read in the same round). If A's write lands after A timed out, B's write (made with the same old etag, or with a newer etag after re-reading) can't also succeed. One of them fails the etag check, and B re-reads and recomputes. Strong consistency is set in blob-store.ts:85. The only effect is an *ambiguous outcome*: A's caller sees "did not answer in time" when the write actually went through. Every operation replays safely: a `holdTime` retry with the same partyId gives `replay: true`, a `moveTime` retry hits the replay branch, and release/confirm are idempotent. See N2 for the one case where the caller might not retry.
4. **Cross-month move race: as documented, not a double booking.** `oldElsewhere` (:319) is read under the old month's lock, which only applies on this server. The new month is written under a separate CAS. A cancel on another server in between leaves a hold at the new time that copies the old state (booked, so it never expires). That is an extra hold the daily warning names, not two parties in one slot, because the new-month CAS still checks rivals. Two moves of the same party racing each other (to different new times) can also both write, because `check` skips the party's own holds. Task 11's record guard has to keep these apart, and the comment says so. Acceptable.

## Minor (new, non-blocking)
- **N1. The `extendHold` rebuild can bring back a cancelled party's time.** If an owner cancels (`releaseTime`) and a late `extendHold` for that party then runs (for example a delayed Task 9 link outcome), the rebuild writes a fresh `held` hold. With `untilIso: null` it never expires. The rebuild also checks against `others = []` (:264), so classes, blocked time and closed days aren't checked. That matches `confirmTime`'s "paid wins" policy. Ask Task 9/13: should the "Party hold with no party" warning also cover a hold whose party record is cancelled? Alternatively, have the delayed caller check the record before calling `extendHold`.

Task 11 should either tell the owner to retry the move (the replay then succeeds and the normal release follows) or name the orphan in the alert.
