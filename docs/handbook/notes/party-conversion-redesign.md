Party booking was redesigned for conversion on 2026-07-09 (commits 718d092..ef9b1fb, **deployed to production same day**). Apple Pay domain registration ran successfully post-deploy — status VERIFIED, so Apple Pay + Google Pay + card are all live. All FAQ answers are filled (10 entries, policies from Kaden: treat+water only w/ 30m optional break; minimal decor w/ 30m early setup + guest teardown; no refund, store credit ≥2wk out, free reschedule ≤7d; everyone who crafts pays, spectators free).

- **Modal flow** is now dynamic `craft → when → who → pay` driven by the pure lib `src/lib/party-steps.ts`: preselected non-personalized craft drops the craft step, a matched `?start=` deeplink drops the when step; progress counts only visible steps. Personalized crafts always keep the craft step (acknowledgment checkbox lives there).
- **Deeplinks:** `?craft=`, `?start=` (exact slot), and NEW `?date=YYYY-MM-DD` (calendar day chip → date preselected, user picks time).
- **Guests: 10 minimum** (`partyConfig.minGuests`, added 2026-07-09 — stepper floor, quick picks 10/15/20/25, copy, and book.json validation all derive from it), default 10, max 30. **Min-guests change is on dev ONLY as of Jul 9 — Kaden said "don't deploy to prod yet."** Kaden confirmed a **10-craft minimum at the register** — all "pay for who comes" copy carries the qualifier and there's a dedicated FAQ ("Is there a minimum party size?"). 11 FAQ entries total.
- **Studio fee is $300 as of 2026-07-09** (was $200) and `partyConfig.basePriceCents` is the SINGLE source of truth: the charge, modal, hero hold-line, FAQ, how-it-works, per-person math, and sticky CTA all derive from it (party-content.ts builds its strings from a `FEE` template). Kaden explicitly wants price changes to be one config edit — never hardcode the fee in copy. Square catalog item price kept in sync via API.
- **Wallets:** PaymentForm accepts `wallet={{amount,label}}` + `onWalletToken`; Apple Pay/Google Pay render only when the SDK initializes them. Domain registered + VERIFIED 2026-07-09 via `scripts/register-apple-pay-domain.ts`.
- **BNPL:** Afterpay (pay-in-4) coded 2026-07-09 behind `wallet.bnpl` (parties only — workshops never get it, Kaden's explicit wish). **Kaden DECIDED NOT TO ENABLE it** (~6% merchant fee "giving away money" while bookings are healthy) — code ships dormant, button self-hides until the account is onboarded in the Seller Dashboard. Don't re-pitch enabling it unless he raises booking trouble. Klarna is NOT supported by Square. **Apple Pay button rule:** always load Apple's apple-pay-sdk.js (all browsers) and render the `<apple-pay-button>` custom element it registers — NEVER a hand-rolled button: `-webkit-appearance: -apple-pay-button` is Blink-ignored (invisible button) and a text child overlaps the native graphic in WebKit. The SDK also enables the desktop-Chrome QR flow (verified initializing in Kaden's Chrome: canMakePayments true). Wallets pre-flight name/email via `canPayWithWallet` prop. Branch previews lack Square env vars so /api/party/* 500s there — wallets are only testable on prod/localhost. Pottery Painting demo item DELETED from Square 2026-07-09.
- **CRITICAL app-ID rule:** the party flow must run the Web Payments SDK under OUR application (from client-config) — `CLASS_BOOKING_APP_ID` is ONLY for the workshops buyer-classes API. Under the widget app, `payments.applePay()` throws (domain registration is per-application) and the Apple Pay button silently never renders on ANY Apple device. Bug found+fixed 2026-07-09 (commit 8a1ae0b, cherry-picked to main as 7acafdc).
